## Added latency per hop (fakes: retrieval 30 ms, planner call 150 ms; `chat/agentic.py`, sequential sub-queries)
| rounds x sub-queries | total | over one retrieval |
|---|---|---|
| 1 x 2 | 241 ms | +211 ms (8.0x) |
| 1 x 4 | 301 ms | +271 ms (10.0x) |
| 2 x 2 | 451 ms | +421 ms (15.0x) |
| 3 x 4 (the defaults, worst case) | 842 ms | +812 ms (28x) |

A loop that stops after the first planner call ("done") costs one planner call (~150-300 ms for a small model). Against a
~100 ms retrieval baseline the "<= 3 x baseline" budget cannot hold for any turn that plans, so the budget needs an absolute form
(for example baseline + `agentic_timeout_s`, default 30 s, with the first SSE frame at once). Mitigations if the eval wants
less: lower `agentic_max_steps` / `agentic_max_subqueries`, or run the sub-queries of a round in parallel (needs one
session per sub-query; not done).

In chat the loop runs inside the stream: the first `meta` frame (`{"agentic": true}`) is sent before any planner call, then
`progress` frames per round, then `meta.subqueries`. No database connection is held during planner calls.
