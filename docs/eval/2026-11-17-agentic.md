## PASS criteria (plan Task 8)
- `multihop` scope passes the standard gain gate (`eval/gate.py`) and the `all` scope delta `p_ndcg@10` >= -0.005.
- Budget (**ledger ruling 2026-11-17, replaces "retrieval p95 <= 3 x baseline"**): absolute. Added latency p95 <= 1.0 s per
  planning round and at most 3 rounds (`agentic_max_steps` = 3), i.e. <= 3 s added in the worst case.

## Added latency per hop (fakes: retrieval 30 ms, planner call 150 ms; `chat/agentic.py`, sequential sub-queries)
| rounds x sub-queries | total | over one retrieval |
|---|---|---|
| 1 x 2 | 241 ms | +211 ms (8.0x) |
| 1 x 4 | 301 ms | +271 ms (10.0x) |
| 2 x 2 | 451 ms | +421 ms (15.0x) |
| 3 x 4 (the defaults, worst case) | 842 ms | +812 ms (28x) |

The ruling's per-round budget is met with room: one round of 4 sub-queries costs ~150 ms planner + 4 retrievals (fakes: 271 ms); a real
small-model planner call (150-300 ms) plus 4 real retrievals (~100 ms each) is about 0.5-0.7 s. A loop that stops after the first planner call ("done") costs one planner call (~150-300 ms for a small model). The old "<= 3 x baseline" form could not hold for any turn that plans, hence the ruling above. Mitigations if the eval wants
less: lower `agentic_max_steps` / `agentic_max_subqueries`, or run the sub-queries of a round in parallel (needs one
session per sub-query; not done).

In chat the loop runs inside the stream: the first `meta` frame (`{"agentic": true}`) is sent before any planner call, then
`progress` frames per round, then `meta.subqueries`. No database connection is held during planner calls.
