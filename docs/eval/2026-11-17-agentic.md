## Added latency per round (fakes: retrieval 350 ms as measured in the perf report; planner 0.5-1.5 s)

Per planning round = one planner call + the round's sub-queries. Sub-queries now run IN PARALLEL (each on its own session,
at most `agentic_max_parallel` = 4 in flight process-wide), so a round costs planner + one retrieval, not planner + N:

| planner | 2 sub-queries sequential | parallel | 4 sub-queries sequential | parallel |
|---|---|---|---|---|
| 0.5 s | +1.2 s | **+0.85 s** | +1.9 s | **+0.85 s** |
| 1.0 s | +1.7 s | +1.35 s | +2.4 s | +1.35 s |
| 1.5 s | +2.2 s | +1.85 s | +2.9 s | +1.85 s |

Three rounds with a 1.0 s planner and 4 parallel sub-queries: +4.05 s total (+1.35 s per round).

**Planner model (re-ruling 2026-11-17):** `agentic_planner_model` (`ROR_AGENTIC_PLANNER_MODEL`; empty = the first chat model). Use a small fast
model: dev uses `qwen2.5:3b` (already on game-01). The budget stays **added p95 <= 1.0 s per planning round**, and the eval run
must be taken WITH that planner: record the planner's own p95 (target <= ~0.65 s with a ~350 ms retrieval) in the compare report.

**Against the ruling (added p95 <= 1.0 s per round): attainable only with a planner call <= ~0.65 s** (round = planner + one
~350 ms retrieval). With a 1-2 s planner a round costs 1.35-2.35 s, so the ruling needs either a faster planner model, a
lower `agentic_max_steps`, or a re-ruling (for example <= 1.5 s per round, <= 2 rounds). `agentic_call_timeout_s` is now 1.5 s: a
slower planner call is dropped and the loop simply stops with what it has (no extra latency beyond the timeout). The eval
runner uses the same parallel path when it has a session factory (`roracle eval run|compare`); the worker `eval_run` job keeps
the sequential path (its pool is 3+1), which over-states latency by (N-1) retrievals per round: take the budget from the CLI/compare
run.

In chat the loop runs inside the stream: the first `meta` frame (`{"agentic": true}`) is sent before any planner call, then
`progress {step, of, done}` per round start/end (the UI shows "Searching sub-question i/n"), then `meta.subqueries`. No
database connection is held during planner calls. MCP `ask` keeps `agentic_answer_reserve_s` (20 s) of its budget for the answer.
