# Performance report, 2026-11-17 (Task 10.13)

Measured with `roracle perf suite --profile full` (see `README.md`) against a synthetic corpus, on one workstation.
Every number below is a measurement unless it is marked **extrapolated**. Budgets: `budgets.yaml` (plan Task 10).

## Findings made while measuring (all fixed or recorded)

**F1. Postgres JIT made `/search` 4x slower under load.** With the default `jit=on`, the generic plans of the ACL
queries (never-executed subplans over `documents` inflate the cost estimate past `jit_above_cost`) were JIT-compiled per
statement: 150-500 ms each, four Postgres backends at 100 % CPU at 4 rps, `/search` p95 1.3 s. With `jit=off`: p95 314 ms at the
same rate. **Fix:** `postgres.parameters.jit: "off"` in the chart; the perf suite sets it on its scratch database. Operators
with their own Postgres must set `jit = off` (OLTP workload).

**F2. Uniformly random unit vectors are the worst case for HNSW.** The first corpus used random 768-d vectors: filtered kNN took
0.6-1.1 s per query (the graph has no structure), `/search` p50 450 ms even at 1 rps. Real embeddings cluster. The generator now
draws vectors around 1,000 topic centres (cosine to the centre ~0.86) and the stand-in query embedder returns a point near a
centre: kNN 5-30 ms. **This is the favourable case**: queries land next to a centre (~1,000 documents per centre), i.e. they are topical; off-topic queries sit between the clusters and cost more. The earlier run is kept here as the worst-case bound: **search p95 4.4 s, filtered 8.6 s, chat 38 s at
10 rps with random vectors and default Postgres settings** (run 1, saturated).

**F3. One API process is CPU-bound near 10 rps.** An unfiltered search costs ~50 ms CPU, a filtered one ~90 ms (two passes, JSON
parsing of 100 hits, response building). Budgets hold per process at the rates in the table; capacity planning should size API
replicas as rps / 10 (search) and rps / 5 (filtered).

**F4. The reconcile gate counted the wrong thing.** "0 ES writes" ignores drift that is only *enqueued* (`acl_sync` jobs). A
wrong default label in the scratch corpus enqueued 1,000,000 repairs and still reported 0 writes. The gate now adds the
enqueued repairs.

**F5. Postgres defaults are not the production profile.** With the shared container's 128 MB `shared_buffers` the same
request spent 130 ms in Postgres (`cited_by_counts` 60 ms, `_load` 50 ms, tags 18 ms); with `shared_buffers=3GB` it spends 13 ms.
`capacity-planning.md` already says shared_buffers ~ 25 % of memory; the numbers above depend on it.

## What was extrapolated or approximated

- Browse at 10M documents (measured at 1M).
- Elasticsearch at 10M chunks (measured at 1M; filtered kNN latency grows with corpus and selectivity, M6 in the audit).
- Chat TTFT is the retrieval half only, approximated by a wide `/search`; no LLM, no RAPTOR units.
- Rebuild throughput uses modelled embedding replicas (the page pipeline itself is real).
- Ingest throughput per worker is not measured (docling and the LLM are out of reach); only our overhead is.
- Model latencies are fixed stand-ins (10 ms embed, 50 ms rerank); a slower reranker adds its time one-to-one.
- The 1M-scale numbers cannot be re-run without about an hour of seeding: the final CI-profile run reused the index names and replaced the 1M corpus.
- A single machine ran load generator, API, Postgres and Elasticsearch together; a separate load host would lower
  every number slightly.

## The CI gate

`roracle perf suite --profile ci` (GitLab job `perf`: nightly schedule, web trigger, manual in merge requests) seeds a small fixed
corpus (20,000 documents, 20,000 chunks, 20,000 LSH versions, 100k done + 10k queued jobs), starts a real API, runs every
scenario above and exits non-zero when a budget is missed. Latency limits are multiplied by 1.5 and `min` limits divided by 1.5 for
shared runners; `reconcile_es_writes` stays 0. The same profile on this box, quiet: search 310 ms (limit 600), filtered
285 (750), browse 114 (150), chat 343 (1200), MCP 318 (675), document read 10 (120), claim p99 3.0 (7.5; p50 1.28 informational),
near-dup 5.1 (75), ingest overhead 0.15 s (3), rebuild 1,274 chunks/s (>= 667), reconcile 0.
